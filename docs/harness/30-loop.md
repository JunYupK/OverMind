# 30 · 작업 루프

작업 단위는 태스크 하나다.

    [0] 세션 시작 — log.md HEAD + 태스크 스펙
         ↓
    [1] 실패하는 테스트 작성
         ↓
    [2] 구현  ←──────────────────┐
         ↓                       │ 자동 반송 (최대 3회)
    [3] ./gradlew verify guardrails ─┘
         ↓ 통과
    [4] log.md 갱신 + 커밋 (두 게이트 통과 상태만)
         ↓
    [5] 요청받은 푸시·PR 작업 → 태스크 종료

## 규칙

**자동 반송은 [3]→[2] 구간에만 있다.**
기계 게이트만 판정이 객관적이다. 리뷰어의 "통과"는 자동 반송의 근거가 되지 못한다.

**반송 상한은 3회다.**
같은 실패를 세 번 못 고쳤다면 원인 가설이 틀린 것이다. 네 번째를 시도하지 말고
멈춰서 `log.md`의 "막힌 것"에 적는다. 그 다음은 `superpowers:systematic-debugging`이다.

**Claude Code↔Codex 교차 리뷰는 필수가 아니다.**
사용자 결정(2026-09-02)에 따라 다른 도구의 리뷰를 자동으로 호출하거나,
그 리뷰를 기다리느라 커밋·푸시·태스크 인계를 보류하지 않는다.
구현 담당자는 스펙과 diff를 직접 대조하고 두 기계 게이트를 확인한다.

사용자가 별도로 리뷰를 요청하면 지정한 범위와 도구로 수행하며,
판정은 `50-review-protocol.md`를 따른다. BLOCKING의 수용·기각은 사용자가 정하고,
수용한 수정은 구현과 검증 단계를 다시 거친다. 기각 사유는 변경 세션의 로그에 남긴다.

## 태스크 인계

Claude Code와 Codex는 **태스크 단위로 구현을 이어받을 수 있다.**
Claude Code가 구현한 태스크 다음을 Codex가 맡을 수 있고, 반대도 같다.
현재 태스크의 리뷰를 맡았다는 사실만으로 다음 태스크의 구현 담당이 되지는 않는다.

기본 인계 시점은 현재 태스크의 `verify`·`guardrails`와 필요한 수정,
커밋·푸시·PR 병합까지 마친 뒤다. 사용자가 중간 인계를 지시하면 병합 전에도
이어받되, 작업 브랜치와 미커밋 변경, 남은 검증·리뷰·병합 단계를 명시한다.

인계할 때 `log.md` HEAD에 완료한 태스크, 검증 결과와 미검증 항목, 남은 문제,
다음 태스크를 남긴다. 사용자가 다음 태스크에 함께 포함하라고 지정한 미커밋 변경도
기록한다. 이 변경은 인수자가 보존하고 지정된 태스크의 커밋·푸시에 포함한다.

인수자는 사용자가 다음 태스크의 구현을 맡겼을 때 아래 순서로 시작한다.

1. `00-start-here.md`의 세션 시작 절차를 따른다.
2. 작업 트리와 현재 브랜치, 원격 `master`와 PR 병합 상태를 확인한다. 기본 인계는
   최신 `master`를 기준으로 시작하고, 중간 인계는 지정된 작업 상태를 이어받는다.
   기존 미커밋 변경을 덮어쓰거나 버리지 않는다.
3. 완료된 태스크와 다음 태스크의 경계를 스펙·플랜 및 실제 코드와 대조한 뒤,
   인계받은 다음 태스크부터 구현한다.

**상태 확인·리뷰 요청만으로 다음 태스크를 시작하지 않는다.**
그 요청만으로 코드·문서·로그를 수정하거나 커밋·푸시·PR 병합을 진행하지 않는다.
조회·리뷰 세션의 로그 갱신 예외는 `00-start-here.md`를 따른다.
